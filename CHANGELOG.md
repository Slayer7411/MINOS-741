### changed
* b2b group: when the leader is lost, a follower keeps its tempo and shows "lead lost" in the strip (no tempo jump). Pair protocol version 7.
* b2b group: automatic takeover. When the leader has been silent for 3 s, the remaining Macs agree on the lowest instance id among them and continue at the same tempo and beat; a returning leader joins as follower, TAKT still wins.
* settings (⌘,): regrouped into tabs by task. new first tab ALLGEMEIN (setup, language and zoom, data folder, updates, crash reports, LIVE, start behavior; opens on first start only), new LIVE & SYNC (live readability, two macs, link, DAW bridge, groove). rare options sit on an ERWEITERT sub-page per tab (link at the bottom of each tab; search and deep links open it). favorites: ☆ on every setting, FAVORITEN page, and a ★ popover in the top bar; stored in the settings file.
* files: collection check (papierkorb, remove, duplicates) and set recording (folder and free name) check files off the main thread; the recording starts once the name is ready. unit tests (existence check off main, free name and folder)

### security
* b2b group: followers no longer take the tempo from Link. Link carries no peer identity, so any Link device on the LAN could steer B2B followers. Followers now follow the leader's clock over the authenticated, encrypted pair channel (20 Hz plus offset estimate per link). Link peers only show as info in the strip.
* two macs: session partners follow the leader over the pair clock too (authenticated pairing), not Link. Link devices on the LAN no longer steer a session pair; Link stays an output on both macs.
* two macs: pairing without a code. both macs run X25519 key agreement with commit-then-reveal (a SHA256 commitment over id, name, key and nonce before any reveal), derive a random 32-byte key and show the same six-digit number; the user confirms on both macs, only then the key is stored in the Keychain per peer. the earlier key derived from a six-digit code is gone (an offline brute force of a recorded handshake is no longer possible). handshake (HMAC over nonces) and frames (ChaCha20-Poly1305, per-direction counters against replay) are unchanged. the peer is identified by a random instance id kept locally (not synced), not by the computer name. unpaired peers are refused; settings offer pair / unpair. remote debug is off by default. unit tests (commitment mismatch, same key and number on both sides, different keys, unpaired peer, replay, tampering), e2e scenario `pair-two-instances` (pair-start, pair-confirm, unpair and refused reconnect)

### fixed
* MIDI clock: when the queue ran late, clock bytes were stamped at "now" and left the grid under load; the stamps now stay on the grid
* collection file: writes are durable (temp file synced with F_FULLFSYNC before the rename, folder synced after it), so a crash or power loss cannot leave an empty collection; file permissions of the original are kept
* collection file: writes are serialised by an advisory lock in `~/Library/Application Support/MINOS-741/locks` (not in the collection folder; 5 s wait, then a clear error instead of a lost update); the lock does not stop the other DJ program
* collection file: restoring a backup runs off the main thread (progress shown, the window stays responsive)
* collection file: a change by the other program between reading and replacing is detected right before the replace; MINOS reloads and re-applies its changes instead of overwriting them
* collection file: failures that were swallowed now reach the status line: cleanup of old backups, the conflict backups (`metadata-konflikt.json`, `edits-konflikt.json`, which no longer overwrite an unreadable older file), and the comparison before a restore
* engine: plugin parameter reads and listener setup no longer run under the controller lock (a slow plugin stalled the 5 ms control tick)
* engine: setting an FX parameter writes the plugin outside the controller lock too (an AU parameter write no longer stalls the control tick)
* vst3: parameter edits and restart requests raised by a plugin during audio processing go through a preallocated event ring (256 entries, overflow counted, never blocks) and are handled on the control thread; the audio thread no longer allocates, locks or reloads the plugin
* engine: data race between the audio thread and late deck workers on the sub-block counter (ThreadSanitizer): each worker job carries its own copy
* audio: switching or reopening the output device no longer blocks the UI (up to ~0.5 s); the status line shows `Öffne Audio-Gerät …` until it is open
* files: Explorer start folders and `Im Finder zeigen` check file existence off the main thread (cloud folders could stall the UI)
* TIDAL login: the callback listener on port 7412 accepts IPv4 and IPv6 loopback (`127.0.0.1`, `::1`, so `localhost` works in the browser); never on other interfaces. a timeout shows a clear message (`Anmeldung abgelaufen … erneut ANMELDEN`)
* updates: release downloads redirected to `release-assets.githubusercontent.com` were refused silently (check found nothing). redirect target allowed, https only. `Jetzt prüfen` shows every outcome with its reason; automatic failures go to the status log after the first one
* fx golden test `fxPluginSlotBitIdenticalToOldChain` passes again: its hash was not updated with the glide snap (9f8fd46). the plugin slot output differs from the old chain only where the deck volume glide snaps to its target (from block 9, max 4.99e-5 relative); hash `0x6f8a07943193ddbf`
* browser: track table column widths, order and visibility are stored in the settings (same as ⌘, and the settings file), restored on start and kept when switching tabs or views; the last change is saved when the table goes away or the app quits. unit tests (round trip through the settings, settings without the key)
